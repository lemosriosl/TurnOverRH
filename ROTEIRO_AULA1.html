O -U postgres não é opcional

postgres é o superusuário padrão da instalação. Sem -U, o cliente tenta entrar com o seu usuário do sistema operacional, que quase nunca existe dentro do banco. Vale para o createdb e para o psql.

Sim — validacao_congelada é o seu conjunto de teste

É o mesmo X_test da Aula 4. O que muda é que agora ele tem nome, endereço fixo e um papel na operação, não só no notebook. Três coisas justificam isso:

  1. O modelo nunca vê essas linhas. Medir no que ele estudou é como corrigir a prova com o gabarito que o aluno escreveu. O número sai alto e não significa nada.
  2. "Congelada" é a palavra que carrega o peso. Ela não muda de uma aula para a outra. Quando a v2 aparecer na Aula 2, o F1 dela vai ser medido exatamente nas mesmas 4.800 pessoas — comparar em conjuntos diferentes é a forma mais comum de promover um modelo pior sem perceber.
  3. É ela que vira o baseline no MLflow. As métricas que o Passo 5 registra saem daqui. Sem esse número gravado, "o modelo piorou" é opinião.

Guarde duas ressalvas para a Aula 2. Um conjunto de teste usado muitas vezes para escolher entre modelos vai deixando de ser cego — cada decisão tomada olhando para ele vaza um pouco de informação. E se a população mudar, o juiz envelhece junto: julgar um modelo feito para o mundo novo com o teste do mundo velho reprova exatamente os modelos que você precisa promover.

A regra que vale para as quatro aulas

Se "champion" aparecer digitado dentro do main.py, você tem a mesma decisão escrita em dois lugares. No dia em que ela mudar, um dos dois fica para trás e ninguém percebe até a produção responder errado. Um único lugar por decisão.

Três decisões de negócio disfarçadas de constante

LIMIAR_DECISAO = 0.5 é onde o modelo separa classe 0 de classe 1. FAIXA_ATENCAO e FAIXA_ALERTA são as cores do card no front. Repare que a primeira faixa termina exatamente no limiar — verde é, literalmente, "classe 0". Nada disso é matemática: é a Marina que decide, e por isso mora aqui e não dentro do modelo.

O MLflow não é uma biblioteca que você importa e sobe. É um serviço, como o Postgres: você liga pelo terminal e ele fica lá. Nada no projeto configura ou inicia esse servidor — a única coisa que liga os dois mundos é a linha mlflow.set_tracking_uri(...) que você acabou de escrever no config.

ArgumentoPara quê
--host 127.0.0.1em qual interface de rede escutar. 127.0.0.1 = só a sua máquina. Se fosse 0.0.0.0, qualquer um na rede alcançaria o servidor
--port 5000a porta. Se já estiver ocupada (no macOS o AirPlay usa a 5000), troque para 5001 e ajuste o MLFLOW_URI no .env
--backend-store-urionde gravar runs, params, metrics, tags e o catálogo de versões. É o banco mlflow que você criou vazio no Passo 1 — o MLflow monta as 19 tabelas sozinho na primeira subida
--default-artifact-rootonde gravar os arquivos: o modelo serializado, a signature, os relatórios. Aqui é a pasta local ./mlruns; numa empresa seria S3 ou MinIO
Erro de senha aqui? O MLflow não lê o seu .env

O .env só é lido pelo seu código Python, através do config.py. O servidor do MLflow é um processo separado e recebe a conexão pela linha de comando — se o seu usuário não for turnover, o comando acima falha com password authentication failed.

Sobre o python -m

Se você instalou por pip, o executável mlflow pode não estar no PATH — o sintoma é command not found mesmo com o pacote instalado. python -m mlflow chama o mesmo programa pelo interpretador que você está usando, e funciona sempre.

As funções do MLflow — parte 1

As três que preparam o terreno. Todas aparecem no onboard_v1.py que você acabou de escrever.

mlflow.set_tracking_uri(uri)

Diz para onde mandar tudo. É um estado global do processo: depois dessa chamada, toda função mlflow.* vai falar com aquele servidor.

Sem ela, o MLflow não reclama — ele silenciosamente grava numa pasta ./mlruns local. O sintoma é sempre o mesmo: "rodou, não deu erro e não apareceu na tela". Se acontecer com você, procure uma pasta mlruns nova no diretório de onde você rodou o script — os seus dados estão lá, no lugar errado.

mlflow.set_experiment(nome)

Escolhe a gaveta onde os runs vão cair, criando se não existir. Um experimento agrupa runs que respondem à mesma pergunta.

A tentação é criar um experimento por aula ou por tentativa. Não faça: a tela de comparação do MLflow só compara runs do mesmo experimento. Treinos, retreinos e monitoramentos do turnover caem todos em turnover_rh — é isso que vai permitir, na Aula 2, pôr v1 e v2 lado a lado numa tabela só.

mlflow.start_run()

Abre um registro e devolve um objeto com run.info.run_id — o identificador que você usa para reencontrar tudo depois.

Use sempre como with. Ao sair do bloco o run é fechado e marcado FINISHED — e se estourar uma exceção no meio, ele fecha como FAILED em vez de ficar pendurado como RUNNING para sempre. Tudo que você logar dentro pertence a esse run; o que estiver fora vai para um run órfão que o MLflow cria sozinho.

Um run é a unidade de "uma coisa que eu fiz e quero poder reencontrar". Nesta disciplina: um onboarding, um retreino, um monitoramento.

Na dúvida entre os quatro

param = escolhi antes · metric = medi depois · tag = quero filtrar por isso · artifact = é um arquivo.

Por que o MLflow separa isso tudo em vez de aceitar um dicionário

Porque cada tipo vira uma coluna diferente na tela. Param e metric viram colunas ordenáveis na tabela de runs — dá para ordenar por F1 e ver qual max_depth ganhou. Tag vira filtro (tags.tipo = "monitoramento"). Metric com step vira gráfico. Se tudo fosse um JSON solto, nada disso existiria.

teoria

Artefato é arquivo. E é onde a evidência mora.

Param, metric e tag são valores — cabem numa coluna de tabela. Artefato é qualquer arquivo que você quer preso a um run: um CSV, um PNG, um modelo serializado, um HTML. O MLflow guarda no --default-artifact-root, e a interface deixa você navegar e baixar.

A diferença que importa

Métrica responde "quanto"

features_em_drift = 0. Um número, ordenável, comparável entre runs, plotável no tempo. Mas não diz quais features, nem por quê.

Artefato guarda a evidência

O CSV com as 15 linhas, KS, razão de média e percentual de zeros de cada uma. É onde você vai olhar quando a métrica acender — e é onde a feature morta desta aula aparece.

Regra prática

Se você precisa comparar entre runs, é métrica. Se você precisa abrir e ler para entender, é artefato. Quase todo incidente precisa dos dois: a métrica avisa, o artefato explica.

O que não deve virar artefato

O dataset inteiro. É a tentação óbvia — "assim fica reproduzível" — e enche o disco em uma semana. Para isso existe o log_input, que guarda nome, formato e digest sem duplicar as linhas.

Nada ali é mentira. O problema é que quatro das seis linhas são declarações, não observações — foram digitadas por alguém depois do fato. Se o .pkl tivesse chegado por e-mail de um colega que saiu da empresa, nem os hiperparâmetros existiriam.

Da v2 em diante isso muda sozinho

Porque a v2 vai nascer dentro do MLflow: o mesmo script que lê o dado é o que treina e o que registra, na mesma execução. O log_input passa a gravar o digest do dado que o .fit() realmente recebeu — não o que alguém acha que recebeu.

Por que a tag em vez de simplesmente omitir

Um run sem informação de lineage e um run com lineage reconstruído parecem iguais na tela. A tag é o que separa os dois. Marcar a própria incerteza é mais útil que escondê-la — na Aula 2 vocês vão ver os dois runs lado a lado e a diferença explica sozinha.

teoria

O MLflow versiona o modelo. E o resto?

Nesta disciplina o que ganha número de versão é o modelo em produção — v1, v2, v3, com aliases apontando para elas. Mas modelo é só uma das quatro coisas que precisam de histórico, e vale saber onde estão as outras três.

O queComo o MLflow trataSuficiente?
Modelo Model Registry: versão numerada, alias, link para o run que a gerou ✓ sim. É o forte da ferramenta
Ambiente log_model grava requirements.txt e conda.yaml junto do modelo ✓ sim, e resolve o problema do .pkl solto
Dado log_input guarda nome, formato e um digest — uma impressão digital do conteúdo ~ referência, não versão. Ele detecta que o dado mudou; não te devolve o dado antigo
Código uma tag com o commit, se você lembrar de colocar ✕ não. Quem versiona código é o git
Versionamento de dados de verdade é outra ferramenta

O digest do log_input responde "esse dado é o mesmo de antes?" — e só. Para responder "me devolva a tabela exatamente como estava em janeiro" você precisa de DVC, LakeFS, Delta Lake ou snapshots do próprio banco. É por isso que o run da v1 fica marcado lineage=incompleto mesmo depois de tudo: metade da cadeia mora fora do MLflow.

O autolog é ótimo para explorar

Uma linha antes do .fit() e ele captura hiperparâmetros, métricas de treino, o modelo e a signature. Na fase de experimentação, em que você roda vinte variações, economiza muito.

E ruim para produção

Ele registra o que ele decide, com os nomes que ele escolhe, e muda entre versões da biblioteca. As suas métricas de negócio, as tags de motivo e o dataset de origem continuam sendo sua responsabilidade — e são justamente o que importa num incidente.
